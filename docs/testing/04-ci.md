# 04 — CI (`.github/workflows/test.yml`)

Three jobs: Linux unit tests, Linux end-to-end tests, and Windows unit plus end-to-end tests.

```
push/PR ──┬── unit     (Ubuntu)
          ├── e2e      (Ubuntu, up to 20 min)
          └── windows  (unit + e2e)
```

## Workflow-level guards

- **`permissions: contents: read`** — the workflow needs nothing more; least privilege
  by default.
- **Concurrency group per ref with `cancel-in-progress`** — pushing twice in a row
  cancels the stale run instead of burning runner minutes on code nobody will look at.
- **Every job has an explicit `timeout-minutes`** — the default of 360 minutes is a
  bill waiting to happen when something hangs.

## job: unit

ubuntu-latest, node 22, python 3.12.

ffmpeg is installed with `sudo apt-get install -y ffmpeg` in both Linux jobs. Two lessons
are baked into that choice, both learned from red CI runs:

- **ffmpeg is not preinstalled on current ubuntu-latest runners.** Do not assume the
  image provides it — install it explicitly and verify the binaries loudly in the same
  step, so an image change fails at the install step, not deep inside a test.
- **Do not reach for a third-party action for this.** The original workflow referenced
  one that did not exist at all, which kills the job at "Set up job" before a single
  step runs — and the failure message gives no hint that an action reference is the
  problem. Rule: every `uses:` line must be checked against the GitHub API
  (`api.github.com/repos/<owner>/<repo>`) before committing. apt is the runner's own
  package manager; prefer it over an unverifiable external action.

```bash
npm ci --ignore-scripts --no-audit --no-fund
npm test
```

`npm ci` validates the committed root lockfile; `npm test` is the behavioral step. **The npm scripts are the single source of truth** — the
workflow deliberately does not enumerate test files. A new test file added to
`package.json` is automatically in CI; a file added only to a workflow list is a file
forgotten everywhere else.

## job: e2e

Same base, plus browser provisioning:

```bash
npm install --no-save playwright-core@<locked-version>   # CLI for the install step
# cache ~/.cache/ms-playwright, keyed by the exact resolved playwright version
npx playwright-core install chromium --with-deps || npx playwright-core install chromium
PYTHON=python npm run test:e2e
```

- **Browser caching — yes, this one.** Chromium binaries are ~170 MB, revision-locked
  to the exact playwright version, and unchanged for months at a time. The cache key is
  the locked `playwright-core` version, so a version bump misses cleanly and re-caches
  — there is no stale-restore failure mode. This is the single biggest time save in the
  workflow.
- **`timeout-minutes: 20`** — the suite renders real video; a hang must not burn
  unlimited runner minutes.
- **`PYTHON=python`** — makes the python resolution deterministic on the runner instead
  of relying on the `py`/`python3` fallback chain.
- **The `--with-deps` fallback** — `--with-deps` needs apt privileges that can fail in
  some runner images; the plain install retry covers that case. If both forms fail the
  step fails loudly, which is correct — chromium cannot run without its system libraries.

## What is deliberately not cached

**npm packages.** Scaffolded test projects install into temporary directories with `npm ci`
from the committed template lockfile. The installs are small; caching `node_modules` across
that indirection buys little and adds a correctness surface. Revisit only if e2e time becomes
a real problem — measure first.

## Reproducing CI locally

The CI commands are exactly the npm scripts — there is no CI-only magic:

| CI step | Local equivalent |
|---|---|
| unit job | `npm test` |
| e2e job | `npm run test:e2e` |

Differences to expect locally: golden stills are committed fixtures. A missing golden fails the run unless `AIYU_WRITE_GOLDENS=1` writes them on purpose. CI also runs a `windows` job and uploads the e2e workspaces when a job fails.
See [03-e2e-tests.md](03-e2e-tests.md) for the semantics.

## Rules for extending CI

1. **New test files go in `package.json` scripts only.** The workflow must never
   enumerate files — that duplication is how tests silently stop running.
2. Keep unit fast. If a new test needs a browser or a render, it is e2e — put it there.
3. Any new cache needs a key tied to the exact thing it stores (like the playwright
   version key). A cache that can restore stale content is worse than no cache.
